# v0.3 Era — Feature Brainstorm

> **Author:** Pre-Phase-4-completion planning session, 2026-05-16. v0.2 arc lands at end of Phase 4 (currently in flight). This doc is the seed for tomorrow's plan/scope conversation — NOT a committed roadmap yet, just options on the table with research backing each.

## Frame

End-of-v0.2 ships a daily-driveable AI dev environment with workspace context, harness pull-through, native session continuation, remote-Bash, multi-user awareness, and polished UX. v0.3 era is about **expanding the assistant's input/output surface** and **enabling multi-agent workflows**. The user already flagged two: better TTS, image drag-and-drop. Below is the user's two plus a wider option set with concrete tech anchors for each.

## User-requested

### Image input (drag-drop, paste, click-to-attach)

**Status:** zero support today. `EmptyState.svelte` has no DnD wiring; `Composer.svelte` is a plain textarea. The CLI accepts image content blocks today via `--input-format stream-json` with the Messages-API shape `{type: "image", source: {type: "base64", media_type: "image/png", data: "<b64>"}}`. We currently use `--input-format text` ([mod.rs:621](src-tauri/src/assistant/mod.rs#L621)), so the wire change is small: switch input format conditionally to stream-json when an image is attached, post a multi-part content block with text + image.

**Plumbing needed:** Composer.svelte gains drag-over highlight, paste handler (clipboard image), and a small attach button (📎 icon). Attached images surface as thumbnail pills above the textarea. On send, frontend encodes each as base64 + media_type, ships via the existing `assistant_send` invocation with a new `attachments` field. Backend in `mod.rs::assistant_send` switches `--input-format stream-json` when attachments are present, serializes a multi-block content array on stdin, includes thinking-block prelude if needed.

**Caveats:** Claude Sonnet 4.6 and Opus 4.7 are vision-capable; Haiku 4.5 is also vision-capable. So no model gating needed. Per-image base64 inflates payload — cap at ~5 MB raw / ~7 MB base64 per attachment, max 5 attachments per turn. Cost: vision tokens are roughly `(width × height) / 750` tokens per image. Surface estimated cost in the composer when attachments are pending.

**Effort estimate:** half to full day. Composer DnD is the bulk of the work; wire plumbing is small.

### Better text-to-speech

**Status:** zero in Rift today. User is using an external tool currently. Three real options ranked by quality vs friction:

**Option A — Web Speech API (zero friction, mediocre quality).** WebView2 already supports `window.speechSynthesis`. `getVoices()` enumerates whatever's installed on the user's Windows machine — by default that includes some SAPI voices plus Edge's neural voices when present ("Microsoft Aria Online (Natural)", "Microsoft Christopher Online (Natural)"). Quality varies wildly. A read-aloud button on each Claude bubble in `MessageBubble.svelte` is ~30 lines of code. No new deps, no API key, no network beyond what Edge does for its own neural voices. Baseline-supported since 2018.

**Option B — Edge TTS via API call (free, high quality).** Microsoft's neural voices are accessible via a public endpoint that the `edge-tts` libraries (Python, Node, Rust ports exist) hit directly. No auth required. Same voices as Option A's "Online (Natural)" ones but more reliable cross-machine, faster, and can be cached per-utterance. Slight implementation cost: write a small `tts.rs` module that POSTs to the Edge TTS endpoint and returns audio bytes. Cache by `hash(text + voice)` on disk to avoid re-hitting for repeated playback.

**Option C — ElevenLabs / OpenAI TTS (paid, premium quality).** Requires API key in Settings, per-character cost. Best quality but adds an auth surface and recurring cost. Probably not the right pick for v0.3 unless user specifically wants it — Option B gets 80% of the quality at $0.

**Recommendation:** ship Option A as the default (every Claude bubble gets a 🔊 read-aloud button) AND Option B as a "Better voices" Settings toggle that switches the backend to the Edge endpoint. User picks quality vs zero-network preference. Combined effort: half to one full day.

### Effort-level selector

**Status:** zero UI exposure today; the CLI flag exists. `--effort` accepts `low | medium | high | xhigh | max`, available levels depend on the model (Haiku probably caps at high, Opus 4.7 supports max). Currently every Rift turn fires at the CLI's default effort, which means you're either over-paying for trivial questions or under-thinking complex ones with no control.

**Plumbing:** add `effort` to `AssistantConfig` like `max_budget_usd`, add two Tauri commands (`get_effort`/`set_effort`), append `--effort <level>` in the spawn at `mod.rs:assistant_send`. Frontend: the existing model picker pill at the bottom-right of the composer ([Composer.svelte:329-341](src/lib/components/assistant/Composer.svelte#L329-L341)) becomes a two-row picker — model on top, effort on bottom — or a small inline selector next to it ("Sonnet 4.6 · medium"). About 2 hours including UI polish.

**UX nuance:** "max" should warn the user since it can burn significantly more tokens. Default to "medium" (the CLI default in scripted mode) and let the user dial up for hard problems. Pair naturally with the per-turn cost cap from Phase 2 so an accidental "max" still hits the budget guardrail.

**Effort estimate:** ~2 hours.

## Strong adjacent additions (high impact, low cost)

### Voice input (STT)

Pairs naturally with TTS. WebView2 supports `window.SpeechRecognition` (Web Speech API). Mic button next to the composer's send button; press-and-hold or click-to-toggle. Real-time interim results display as you speak; commit to the textarea on end-of-utterance. Quality is decent on Edge (uses Azure Speech under the hood when online). About 1-2 hours of frontend work. Combined with TTS this gets you full hands-free Assistant operation — useful for when you're debugging the FiveM server and want to ask Claude something without breaking flow.

### Multi-root workspaces

Roadmap noted gap. CLI supports `--add-dir` for additional working directories. UI surface: workspace chip in `AssistantHeader.svelte` becomes a multi-select, EmptyState.svelte's open-folder button becomes a "Add folder" / "Switch workspace" menu. Backend in `assistant_set_root` becomes `assistant_set_roots(Vec<String>)`. Spawn appends `--add-dir <path>` for each root past the first. About half a day. Useful when working across FiveM resources + a separate tooling repo simultaneously.

### Conversation export / share

Markdown export per conversation — load JSON, walk messages, emit `# User`/`# Claude` sections. Optional: a "share link" mode that uploads to a GitHub gist via the user's gh CLI (we already have GitHub plumbing for release uploads). Useful for asking Trey to review a Claude session. About 2-3 hours.

### Snippet / saved-prompt library

Slash command `/snippet` opens a small picker of pre-saved prompts. User authors via Settings or a `~/.rift/assistant/snippets/*.md` directory (one file per snippet). The slash-menu in Composer.svelte gets a new branch for snippets alongside the existing /new, /history, /model entries. Half a day. Heavily used in Cursor + Continue.

## Multi-agent direction (Phase 5 from v0.2 roadmap, restated)

Background agents via `claude --bg <task>` returning a session ID immediately. Separate panel in Rift (new tab? sidebar section?) listing running/finished/stopped agents with `claude logs <id>` output. Attach/respawn/stop controls. This was Phase 5 of the v0.2 roadmap; folding into v0.3 is fine because by v0.2's end the chat-side is feature-complete. Rough estimate one focused session for the wiring + a half-day for the UI surface design.

## Lower-priority but worth noting

**Themes** — light/dark/custom. Tauri-native CSS variable swap, no logic.

**Keyboard shortcut customization** — surfaces existing shortcuts and lets user rebind. Settings page addition.

**Inline diff-and-apply for AI-suggested file edits outside of Edit tool calls** — when Claude pastes code in a response, a "apply to X.lua" button appears. Niche but powerful for code-review workflows.

**Local LLM fallback (Ollama)** — for offline / private contexts. Big lift (different parser pipeline, different auth model). Skip unless user explicitly wants it.

**Per-project memory** — `.rift/assistant-project.md` file Claude reads on init, both you and Trey edit it in the workspace. Shipped notes/decisions etc. Free MVP because the file just gets prepended to the system addendum.

**In-app MCP / plugin gallery** — discover and install MCP servers via UI. Bigger lift, depends on Anthropic's plugin marketplace direction.

**System tray notifications** — Claude finished long background task → toast. Pairs naturally with Phase 5 background agents.

## Recommended v0.3 sprint shape (preliminary)

If you want a tight, themed arc: **"v0.3 — Multimodal + Multi-agent"**. Three phases:

**Phase A — Multimodal Input (image + voice).** Drag/drop/paste images into composer, mic button for STT input. Half to full day. Unlocks "show Claude this screenshot of the bug" and "tell Claude what to do verbally."

**Phase B — Multimodal Output (TTS read-aloud + per-message audio).** Read-aloud button on every Claude bubble, Edge TTS option in Settings for premium voices. Combined with Phase A gives full hands-free operation. Half to full day.

**Phase C — Background Agents (the Phase 5 from v0.2 roadmap).** `claude --bg` integration, separate UI panel, attach/respawn/logs. One focused session.

Plus opportunistic adds along the way: multi-root workspaces (Phase A could include the wiring), conversation export (Phase B touches MessageBubble.svelte anyway), per-project memory (cheap addition to system addendum from any phase).

Total: 3-4 focused sessions. Hits both user-requested items in Phase A+B, lands the multi-agent feature in Phase C, and the theme — "expand what you can put into and get out of the assistant" — is coherent enough to message as a single release.

## Parking lot — v0.4+ "Full UI rework" (NOT for this arc)

User raised this 2026-05-16 as a heads-up: because the Assistant has expanded into a primary mode of using Rift, the surrounding UI (TabRail, AppShell, Settings layout, status bar, dock placement) deserves a holistic rethink to evolve around it. This is explicitly OUT of scope for v0.3 — capture-only so it doesn't get lost.

Likely scope (don't plan yet, just enumerate so future-us has a starting list):

Customizable layouts — Tasks dock could be detachable / floating / resizable; HistoryDrawer could pin open as a left sidebar; multi-pane workspace ("coding scene" vs "server monitoring scene" vs "chat-only scene") with saved layouts the user switches between. Tauri 2 supports multi-window so floating panels are technically feasible.

Full theme system — not just light/dark, but accent color, font family, density (compact vs comfortable), background image / blur, opacity (the Rift-themed dark is fine but isn't customizable beyond that today).

Custom keybinds — surface every shortcut in Settings, allow rebinding. Today there's some kbd hints in the composer hint row, but no central reassignment.

Settings reorganization — Settings.svelte is 1060L and growing; a v0.4 rework might split into sub-pages or use a hierarchical nav instead of the flat-list-of-sections.

Status bar customization — current titlebar is fairly fixed; could expose user-selected pills (current branch, drift count, Trey-presence, etc).

Command palette parity — Ctrl+K currently does "search or run a command" but it's narrow; could become the universal entry point for everything (open files, switch convos, set model, run snippets, jump to settings).

Plugin/extension surface — let users add their own panels (Cursor/VS-Code style). Big lift, depends on a stable Tauri+Svelte plugin contract being designed. Probably v0.5+ territory.

Default scenes / first-run UX — when you launch Rift, get a scene picker ("Server work" / "Solo coding" / "Pair with Claude") that pre-arranges the layout instead of every user having to discover the dock toggles themselves.

When the time comes to plan this, it's its own multi-session arc — not a single phase. Worth treating it like the v0.2 Assistant arc: research → roadmap → sequential phases with verification gates.
