## v0.20.6 — 2026-06-17 — Update + CLI-detection robustness (round 2)

> **Why.** Continuing the user-end "fails to detect / can't update" hardening, an audit of the self-update path and the CLI resolution path surfaced two more ways a real environment change went silently undetected on a user's machine (both invisible on a dev box). The self-update download/apply chain itself (timeouts, stall watchdog, epoch guard, child-reap, R2 feed) was verified healthy end-to-end and left untouched.

**Fixed:**
- **Update check now auto-retries a transient failure.** The launch check (`updates.svelte.ts`) had no short retry — an offline-at-launch user, or a momentary R2 feed blip, landed in `error` and got no re-check until the **6h** auto-tick, so they could sit a whole session unaware a release shipped. Added a bounded backoff (30s / 2m / 5m), reset on success, in-flight-download-safe, cleared on dispose. Mirrors the v0.20.5 CLI-update retry.
- **"CLI present" pill can no longer lie to turn spawns.** `assistant_auth_probe` re-enumerates installs *fresh*, but `claude_command()` (auth-status **and every real turn**) went through the sticky `CLAUDE_EXE` cache, whose `#64` re-stat only re-resolves a *vanished* path — never a cached `None`. So a CLI installed **after** a failed first resolve stayed invisible to sends until restart: the pill flipped green on Re-check, yet every message failed "Claude CLI not found." The probe now syncs the cache to its authoritative active pick (reusing the offloaded enumeration — no extra spawn, no async-thread block), so the next turn resolves the right binary with no restart.

**Verify.** version lockstep ×3 + `Cargo.lock` · svelte-check 0/0 · `cargo check` clean.
