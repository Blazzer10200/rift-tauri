## v0.20.5 — 2026-06-17 — CLI update detection hardening

> **Why.** A user on the latest app version reported Rift failing to detect Claude CLI updates. Audit of the detection path (`cliUpdate.svelte.ts` ← npm `latest` manifest, compared against the backend install enumeration) found two ways a real update could go silently undetected: a transient check failure stuck for the whole session, and a stale CDN-cached registry response.

**Fixed:**
- **Transient check failures now auto-retry.** All three triggers of `maybeCheck` (`HomePage`, `ChatTabsBar`, `SettingsPage`) are `onMount` fire-once, so a single failure — offline at launch, an npm hiccup — left detection silently dead until the next app restart. Added a bounded backoff retry (30s / 2m / 5m), reset on success, timer cleared on teardown.
- **npm registry read bypasses the HTTP cache.** The dist-tag `latest` manifest is CDN-fronted with cache headers, so the webview could serve a stale version and miss a new release. Added `cache: "no-store"` — cheap given the existing once-per-6h throttle.

**Flagged (tracked in `docs/ISSUES.md`, not in this release):** auth/installs only re-probe on discrete events, so an *external* CLI update (terminal `npm i -g …@latest`) leaves the installed version stale until a trigger fires; an install whose `--version` can't be read is invisible to staleness; check-failure is surfaced only on the Settings page.

**Verify.** version lockstep ×3 + `Cargo.lock` · svelte-check 0/0 · vitest `cliUpdate` 23/23. Frontend-only — no Rust touched.
