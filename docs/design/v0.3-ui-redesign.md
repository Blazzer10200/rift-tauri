# Rift v0.3 — UI Redesign Brief

> **Author:** 2026-05-17, post-v0.2.57 prep. Source-of-truth for the v0.3-era UI overhaul. Read [v0.3-brainstorm.md](v0.3-brainstorm.md) first for feature context; this doc is the *shell*, not the features.

## Why this redesign

The v0.2 arc turned the Assistant from a single tab into the daily-driveable centerpiece of Rift. By the end of v0.2 (S69–S74) the Assistant has: harness pull-through, native session resume, workspace context, remote-bash, multi-user shell locks, cost+model badge, @-file mentions, conversation search, streaming pacer, diff cards. **Chat is now where the work happens.**

v0.3 piles on input/output surface (image input, TTS, STT, effort selector, multi-root) + a background-agents panel. Adding all of that to today's "Assistant is one tab among seven" model means **death by a thousand pills**: the composer footer grows unmanageable, panels fight for the same space, and the page-switching mental model doesn't fit anymore — the user rarely leaves Assistant.

This doc defines the v0.3 shell: **one canvas, assistant-centric, with a customizable dock of everything else.**

---

## Decisions locked

| Aspect | Choice |
|---|---|
| Canvas shape | Main column + right-side dock |
| Top level | Assistant-centric, single page (no top-level tabs) |
| Manual escape hatch | Per-panel `⛶ Maximize to center` swap (any dock panel can take over the main column temporarily) |
| Dock side | Right |
| Composer location | Bottom of main column, not detachable |
| v1 dock panels | Tasks · Sync · Files · History · Agents · Terminal · Attachments · Activity Feed |
| v2 panels | Snippets · Diagnostics |
| Settings UX | Slide-over modal w/ internal tabs |
| Theme | Existing OKLCH dark tokens preserved (`app.css`) |
| Density | Existing compact/regular/comfy preserved (`data-density`) |
| Multi-user | Per-OS-user layout preset + first-launch preset picker (Minimal/Standard/Power) |

## What dies

| Thing | Why |
|---|---|
| `type Tab = "browse"\|"activity"\|"sync"\|"assistant"\|"conflicts"\|"settings"\|"diagnostics"` | Replaced by `type PanelId` over the dock library. |
| `visited: Set<Tab>` lazy-mount machinery | Replaced by per-panel `mounted` flag (same idea, generalized). |
| `gotoSettings(section)` function | Replaced by `openSettings(section?: SettingsSection)` modal trigger. |
| Per-tab `Ctrl+1..6` shortcuts | Repurposed: `Ctrl+1..8` toggles dock panels (open/close). `Cmd+,` opens Settings. |
| `.beta-pill` on Assistant tab | Assistant is the surface — no longer "a beta thing you visit." Beta moves to a discrete header pill. |
| `Conflicts` as standalone | Folded into Sync panel as expandable section. |

### Grid spec

```css
.shell      { grid-template-rows: 44px 1fr 22px; }
.middle     { display: flex; flex-direction: column; }
.body       { grid-template-columns: var(--rail-w, 48px) 1fr var(--dock-w, 320px); }
.body[data-dock-collapsed="true"] { grid-template-columns: var(--rail-w) 1fr 0; }
.main       { display: grid; grid-template-rows: 1fr auto; /* chat + composer */ }
```

The `--dock-w` CSS variable mirrors the existing `--rail-w` pattern. Drag-resize via a vertical handle between main and dock writes the new value.

### Min/max widths

| Region | Min | Default | Max | Notes |
|---|---|---|---|---|
| Rail | 48 | 48 | 220 | Existing hover-expand or pinned-220, unchanged |
| Main | 480 | (flex) | — | Below 480 the dock auto-collapses |
| Dock | 0 (collapsed) | 320 | 560 | Drag handle on left edge |

Window minimum width = `48 + 480 + 0` = **528px** when dock collapsed; expanded dock pushes effective comfortable minimum to ~880px.

## Panel system — the dock primitive

A **panel** is the unit of customization. Same component pattern for all 8 v1 panels.

### Panel shape

```ts
type PanelId =
  | "tasks" | "sync" | "files" | "history"
  | "agents" | "terminal" | "attachments" | "activity";

type PanelState = {
  id: PanelId;
  open: boolean;        // visible in dock?
  collapsed: boolean;   // body hidden, only header visible
  order: number;        // position in dock stack
  height: number | null; // null = auto; number = pinned px height (resize handle)
};
```

### Panel header anatomy

```
┌──────────────────────────────────────────┐
│ ▾  Tasks   3                ⛶  ⋮         │  ← 30px header
└──────────────────────────────────────────┘
```

- **Caret** — collapse/expand body
- **Title + count badge** — uses existing `.count-pip` primitive (`app.css:209`)
- **`⛶` Maximize** — swap this panel's body into the main column; chat slides to dock or hides
- **`⋮` Menu** — Close · Settings · Pop out (future: detach window)

### Panel body

- Scrolls independently
- Vertical drag handle at bottom (when height is pinned) resizes
- Drag header up/down to reorder stack

### Add/remove panels

`+ Add panel` button at dock bottom opens a popover:

```
┌──────────────────────────┐
│ Add panel                │
├──────────────────────────┤
│ ☑ Tasks                  │
│ ☑ Sync                   │
│ ☐ Files                  │
│ ☑ Agents                 │
│ ☐ Activity Feed          │
│ ─────                    │
│ Snippets       (v2)      │
└──────────────────────────┘
```

Toggling a panel adds/removes it from the dock stack at `order = max+1`.

## Maximize-to-center behavior

When user clicks `⛶` on a panel header:

1. Panel body swaps into the main column (chat hides).
2. Composer stays at bottom — context for the active maximized panel (e.g. typing a path while Files is maximized).
3. A **"⤴ Restore"** strip appears at top of main column.
4. Dock keeps the headers of all panels (collapsed), so user can swap focus among maximized panels by clicking another header's `⛶`.
5. Clicking `⤴ Restore` returns chat to center.

Per-panel state preserved during swap (Tasks scroll position, Sync diff selection, etc.).

**Why composer stays:** the user might want to ask Claude about whatever they just maximized. Removing the composer for those views would force a context switch. Keeping it is the *raison d'être* of one-canvas design.

## Starter presets (first-launch + Settings)

Three presets ship. Each is just a different `panels: PanelState[]` snapshot.

| Preset | Open panels (top→bottom) | Audience |
|---|---|---|
| **Minimal** | Tasks · History | New users; Trey first-launch default |
| **Standard** | Tasks · Sync · Files · Agents · History | Daily driver (Blazzer-shape) |
| **Power** | Tasks · Sync · Files · Agents · History · Terminal · Activity Feed · Attachments | All-in |

First-launch flow: detect empty `panels` config → show preset picker modal → user picks → save → never asked again. "Reset to preset" available in Settings → Appearance → Layout.

## State + persistence

Extend `ui-prefs.svelte.ts`. Storage stays in `localStorage` (existing pattern); no Tauri command needed (panel layout is per-machine-per-OS-user, not per-server).

```ts
// New keys
const PANELS_KEY = "rift.ui.panels.v1";
const DOCK_WIDTH_KEY = "rift.ui.dock-w.v1";
const MAXIMIZED_KEY = "rift.ui.maximized.v1"; // PanelId | null
```

Mirroring the existing `apply()` pattern: writes `--dock-w` to `:root` style, body `data-dock-collapsed` attr.

**Why localStorage not `~/.rift/`:** layout is UI taste, not portable workspace state. Other users on the same machine get their own layout via different OS profiles. Matches the existing density + rail-pinned precedent.

## Settings as slide-over modal

Internal section nav is **already** there in `Settings.svelte:24` (`type Section = "appearance" | "terminal" | "assistant" | "servers" | "keys" | "about"`). The redesign just changes the host: from "fills the main pane" to "slide-over from right, 560px wide w/ internal tab bar."

Reuses existing `.dialog-shell` / `.dialog-body` styles from `app.css:235-284`. The only new piece is the right-side slide-over transform (vs the centered dialog-in animation).

Trigger: `⚙` gear icon in Titlebar right area, OR `⌘,` (new shortcut), OR cmdK → "Settings".

## Visual design — what's new

90% existing tokens carry over. **New primitives needed:**

1. **Panel header** — a 30px row matching `.dialog-head` but slimmer, no border-radius, hover state.
2. **Panel collapse caret** — chevron-right → chevron-down on open, 140ms ease.
3. **Dock drag handle** — 4px vertical strip on dock's left edge, `var(--border)` default, `var(--accent)` on hover/drag.
4. **Panel reorder ghost** — semi-transparent clone follows cursor during drag.
5. **Maximize transition** — 220ms cubic-bezier swap (matches existing `--rail-w` transition).
6. **Settings slide-over animation** — `transform: translateX(100%) → 0`, 180ms cubic-bezier.
7. **Preset picker modal** — uses existing `.dialog-shell`; 3-card grid.

Zero new colors. Zero new radii.

## Implementation phasing

### Phase A — Shell skeleton (1 session)

Refactor `AppShell.svelte` body grid from `[rail | pane]` to `[rail | main | dock]`. Stub dock with zero panels. Repurpose `TabRail` to toggle dock panels instead of swap pages. Wire `ui-prefs` panel state + localStorage. Settings becomes slide-over modal. Cmd palette commands updated.

**Verify:** dev launches, can toggle stub dock panels open/closed, Settings opens as slide-over, no regressions on Titlebar/StatusBar.

### Phase B — Migrate existing surfaces into panels (1-2 sessions)

Wrap each in a panel shell:
- `TwoPane` → Files panel
- `SyncPage` → Sync panel (Conflicts folded in as expandable section)
- `ActivityFeed` → Activity panel
- `TerminalPanel` → Terminal panel (drop the floating overlay mode; it's a normal dock panel now)
- `Diagnostics` → v2 panel (defer wiring)

Move `HistoryDrawer` + `TasksDock` out of `AssistantPage` into top-level panels.

`AssistantPage` shrinks to just header + chat + composer.

**Verify:** every panel renders, internal state survives toggle, no functional regression on sync engine / file ops.

### Phase C — Maximize + drag-reorder + presets (1 session)

`⛶` swap-to-center wiring. Drag-to-reorder in dock. Preset picker on first launch. Resize handles (dock width + per-panel height).

**Verify:** maximize any panel → chat hides → restore returns; presets apply cleanly; layout persists across reload.

### Phase D — New v0.3 panels (parallel w/ feature work)

- Attachments panel (lands w/ image-input feature)
- Agents panel (lands w/ background-agents feature)

These two are tied to their feature implementations; not part of the shell refactor.

**Total shell-redesign scope: ~3 sessions.** Phase D panels ride feature work, not shell work.

## Risks + rollback

| Risk | Mitigation |
|---|---|
| Trey or another user dislikes single-canvas | Maximize affordance covers it; if escalates, expose "Classic mode" toggle in Appearance to restore tab navigation (kept dead code under feature flag for one release) |
| Migration breaks SyncPage/TwoPane internal state | Each panel migration is independent; ship behind a `RIFT_V03_UI=1` env gate during dev, flip default ON only when all panels green |
| Panel reorder w/ keyboard inaccessible | Up/Down arrows on focused panel header reorder via keyboard; documented in cmd palette |
| Performance regression from always-mounted panels | Existing `visited` Set pattern proves lazy-mount works; carry forward as `panel.mounted` flag — never instantiate a closed panel until first open |
| Dock width too narrow for SyncPage's file table | Min-dock-width 280; horizontal scroll in SyncPage body if narrower; maximize-to-center is the escape hatch for power tables |
| Settings-as-modal loses "always there" navigation | Cmd+, shortcut + cmdK + Titlebar gear icon = three discoverable paths |

**Rollback boundary:** keep the v0.2.57-alpha tag pristine. Develop redesign on a branch (`feat/v0.3-ui-shell`). Merge only after phase C ships green w/ CDP verification.

## Open questions (deferred, not blocking Phase A)

1. **Dock left-side option** — should the dock be left/right user-pickable? (Default right; pickable feels like overkill for v0.3 but trivial to add later.)
2. **Floating-panel mode** — should panels be detachable into separate windows (Tauri `WebviewWindow`)? Useful for multi-monitor; out of scope for v0.3 unless user pushes for it.
3. **Panel groups / tabs within a panel slot** — should the dock support "stacked panels in one slot, switch via tab"? Adds complexity; reject for v0.3 unless real demand.
4. **Composer attachment tray placement** — above composer (inline) or as a thumbnail strip in the Attachments panel? Decide w/ image-input feature, not here.
5. **Mobile/narrow-window degradation** — Tauri WebView2 is always desktop; skip responsive work entirely for v0.3.
6. **Drag-and-drop matrix** — file-on-chat = attachment, file-on-Files = upload, file-on-Sync = ?, etc. Define when feature work lands.
