## Skeleton

| # | Severity | File:line | Issue | Suggested fix |
|---|---|---|---|---|
| 1 | HIGH | `lib.rs:626` | `local_list_dir` takes an arbitrary path from JS, calls `reject_path_traversal` (blocks `..` only), then lists any dir the process can reach — no containment to `local_root`. User can browse `C:\` or `%APPDATA%` via devtools. | Add profile-based containment similar to `validate_local_child`, OR at minimum reject absolute root/drive-only paths and require the path to start with a known `local_root`. |
| 2 | HIGH | `lib.rs:667` | `remote_list_dir` takes an arbitrary POSIX path from JS with zero validation — no `..` check, no `remote_root` containment, no empty/root guard. Passes straight to `SftpClient::list_directory`. | Apply `validate_remote_child` (or an unguarded-read variant that still blocks `..`/empty/root) before the SFTP call. |
| 3 | HIGH | `lib.rs:678` | `upload_paths` jobs are `(local_path, remote_path)` tuples; neither local nor remote side is validated beyond `PathBuf::from`. Local can be an absolute path to any readable file; remote can be outside `remote_root`. | Validate both sides: `reject_path_traversal` + containment on local, `validate_remote_child` on remote. |
| 4 | HIGH | `lib.rs:693` | `download_paths` jobs are `(remote_path, local_path)` tuples with no validation on either side. Remote can be `../../etc/passwd`; local destination can be outside `local_root`. | Same as #3: validate remote w/ `validate_remote_child`, local w/ `validate_local_child`. |
| 5 | MED | `lib.rs:866` | `bootstrap_list_files` takes a caller-supplied `local_root` string and uses it verbatim to build download destinations. If the frontend passes a manipulated value, files are dropped outside the configured root. | Resolve against the profile's `server.local_root` instead of the caller-supplied string, OR canonicalize + require `starts_with(server.local_root)`. |
| 6 | MED | `path_guard.rs:78–91` | `validate_local_child` for non-existent paths canonicalizes the **parent** then joins the raw filename without further validation. A filename containing a `/` or `\` on Windows (e.g. `foo/bar`) would join as a sub-path under the canon parent, potentially escaping one directory level if the parent is right at root. `Path::file_name()` strips everything before the last separator, so `foo/bar` → `bar` (safe), but `PathBuf::from("foo\0bar")` (NUL) or overlong filenames are passed through unchanged. | After joining, assert `canon.parent() == canon_parent` to catch any remaining edge case. |
| 7 | MED | `path_guard.rs:55` | Remote containment check uses `starts_with(&format!("{root_norm}/"))`. If `root_norm` happens to be `/` (profile `remote_root = "/"`), the check becomes `starts_with("//")`, which rejects all paths and prevents using a root-level remote_root. More importantly, profile validation does not prevent a user setting `remote_root = "/"` — if it did succeed, the guard would wrongly block. | Add an explicit reject for `root_norm == "/"` in `validate_remote_child` (line 44 region) and in profile `save_server`. |
| 8 | MED | `path_guard.rs:20–60` | Remote path validation is case-sensitive. On case-insensitive remote filesystems (e.g. Samba share, macOS HFS+), `normalized.starts_with(&format!("{root_norm}/"))` can be bypassed by casing the root prefix differently (`/Resources` vs `/resources`). Not a concern for Linux SFTP targets, but worth a note. | Document the assumption (Linux SFTP target). If Samba/macOS support is added later, add a case-fold step. |
| 9 | LOW | `path_guard.rs:20` | `validate_remote_child` rejects backslashes in the full path (line 25) but not in individual segments after splitting on `/`. A segment could contain a raw backslash on a Samba remote. Low risk on Linux. | Strip or reject `\` per-segment if cross-platform remote support is added. |
| 10 | MED | `lib.rs:454–461` | `enqueue_for_flush_batch` checks `..` via `reject_path_traversal` but does **not** verify the path is under any `local_root`. A crafted absolute path bypasses the traversal check entirely (e.g. `C:\Windows\System32\foo.dll`). | Require paths to be under the engine's watched local roots, or at minimum reject root/drive-only paths. |
| 11 | MED | `lib.rs:469–476` | `resolve_conflict` accepts a `local_path` string, only checks `..` via `reject_path_traversal`, then passes it to `engine.resolve_conflict`. Same absolute-path bypass as #10. | Require path under a watched local root. |
| 12 | MED | `lib.rs:1034–1057` | `editor_for` double-init race: drops first lock, opens SFTP, re-acquires lock, uses `or_insert`. A concurrent second call that wins `or_insert` causes the first caller's `Arc<EditInPlaceManager>` (and its SFTP client) to be **silently dropped**. If the SFTP client has state (open channel, pending ops), the drop could close an in-flight session mid-operation. Comment acknowledges "one wasted handshake" but the drop is silent. | Log a `warn!` on `or_insert` returning an existing value (means wasted handshake occurred). Consider replacing the check-then-act w/ a `tokio::sync::OnceCell` per server key to serialize init. |
| 13 | LOW | `lib.rs:176–222` | `diag_state_pump` acquires `AutoSyncState` lock, calls `engine.status().await` while holding it, then `drop(g)`. `status()` is async and does its own internal locking. Lock is held across an await point — any other command that tries to lock `AutoSyncState` will block during the 500ms pump cycle. | Call `engine.clone()` (or capture `Arc`) under the lock, then `drop(g)` before calling `.status().await`. Same pattern fix as `diag_get_state` (line 76–108) which also holds the lock across `.status().await`. |
| 14 | LOW | `lib.rs:76–108` | `diag_get_state` holds `AutoSyncState` lock across `engine.status().await` (line 79–91). Same issue as #13 — any concurrent command needing the lock is blocked during the async status call. | Same fix: clone `Arc<AutoSyncEngine>`, drop lock, then await. |
| 15 | MED | `diagnostics/mod.rs:277` | `LogForwarder` forwards every log message to the frontend via the diag bus including error messages, which may contain SSH key paths, partial host keys, or SFTP path fragments from `format!` in error branches. The `fields` payload for `DiagStage::Log` includes only `target` (the Rust module path) — no scrubbing. | Audit callers of `log::error!/warn!` in `sftp/`, `tunnel/`, `transport/` for messages that interpolate key paths, host addresses, or error bodies. Strip or redact before publishing. Short-term: accept the risk and document; add a `RUST_LOG_DIAG_SCRUB` env var flag to disable forwarding error-level messages to the bus in production builds. |
| 16 | MED | `diagnostics/mod.rs:84–93` | `DiagEvent.file` field carries the relative path of the file triggering a sync event and is sent verbatim to the frontend over `diag://event`. For files outside the watched root (edge case from #10/#11), this could expose absolute paths to the renderer. | Relativize `file` to the watch root before publishing, or strip to basename only. |
| 17 | LOW | `diagnostics/mod.rs:95–176` | `DiagBus` stores `last_rescan_signal_at` and `last_drift_scan_at` in `std::sync::Mutex`. Both are read on the hot diag pump path (every 500ms). No contention risk in practice, but `Mutex::lock().ok().and_then(|g| *g)` silently ignores a poisoned mutex — if a panic occurs inside `publish()` while the mutex is held, all future reads return `None`. | Use `AtomicU64` (epoch ms) for both timestamps to match the rest of the counters. Eliminates mutex and panic-poison concern. |
| 18 | LOW | `profile/mod.rs:15–39` | `bridge_token` stored as plaintext in `~/.rift/rift.json`. A comment acknowledges this ("Phase 6"). | 21 | LOW | `state/paths.rs:29–33` | `safe_profile_key` silently strips all non-alphanumeric/hyphen/underscore chars. ## Velopack init order — verified

`lib.rs:1119`: `velopack::VelopackApp::build().run()` executes **before** `tauri::Builder::default()`. LogForwarder is installed one line before (line 1117) for stderr visibility during install/update. Order is correct.

## path_guard.rs — summary

Core logic is sound. Skeleton issues above (#6–9) are edge cases for unusual inputs (NUL in filename, root remote_root, Samba). Main gaps in the guard coverage are caller-side: `local_list_dir`, `remote_list_dir`, `upload_paths`, `download_paths` don't call the guards at all (items #1–4).
